# 技术博客写作

## 写作目标

用户通常只给一个概念。主动研究并将它写成一篇面向有一定基础读者的中文 Markdown 文档，用于学习和沉淀理解。默认一个概念对应一篇完整文章，允许长文；围绕约定范围充分展开，不因篇幅长自动拆成系列，也不从零重讲全部基础。

概念较大时，默认完整覆盖理解该概念所需的主要问题，讲清整体脉络、核心机制和主要取舍，关键部分深入展开，允许文章较长。不要自行缩成单一切入点，也不扩展为整个领域的百科；具体覆盖范围在大纲中呈现供用户确认。

这些是用户的默认偏好，具体任务中的新要求优先。技能应可在不同项目使用，不依赖某个固定目录、私人知识库或特定工具名称。

## 判断当前任务

- **新文章**：主动研究，先给出大纲，等待用户确认或调整后再写整篇。确认大纲以前不生成完整正文。
- **大纲已确认**：沿用当前会话中确认的范围与偏好继续写作，不重复要求确认。
- **成稿后的提问或讨论**：先在对话中解释。提问、表示困惑或讨论观点不自动授权改稿。
- **明确要求检查或审阅文章**：启动独立的“核验与通读”，按下文的手动核验方式报告问题；默认不修改文章。普通写作或改稿不会自动启动这一轮审查。
- **明确的修改建议或要求**：阅读当前文章，修改指定内容，并连带调整直接相关的解释、例子、术语和前后引用，保持全文一致；保留其他内容与无关的用户手工编辑，不借局部修改重新组织整篇。不要求重新确认已明确的修改指令；只有修改范围实质不明时才澄清。

## 从概念到大纲

结合模型已有知识拆解概念、形成检索方向，主动查阅相关材料。输入可以只有一个概念，不要求用户先收集链接或填完整简报。若存在影响方向的同名概念或重要歧义，集中询问必要信息；可合理推定的前置知识、范围和版本选择，放在大纲中说明供用户调整。

检索优先考虑相关技术的官方文档、规范、源码、原论文与作者材料；技术博客用于补充解释角度和工程经验。根据主题需要使用可访问的中英文资料。阅读原文，核对关键结论、版本与条件，避免把搜索摘要或模型记忆当成已验证来源。

研究技术的形成与演进：出现前实际采用哪些方案、遇到什么局限、哪些需求促成新设计，以及后续方案解决了什么新问题。关键历史节点和因果判断查证原始提案、论文、规范版本或参与者记录；不要把用于讲解的假设性简单方案当成真实历史。

遇到资料缺口或来源分歧时，默认继续补充检索并自行解决：调整关键词、寻找更直接的原始依据、比较版本和适用条件，原文不可访问时寻找公开的替代来源。不要因初次搜索不足就暂停写作、降低交付目标或把资料判断交给用户。补查后确实仍无法确定的内容，再如实说明或收窄结论；需要用户确定主题含义或范围时才询问。网络或原文不可用时不声称已完成检索。

研究以解释清楚为目标，关键机制按需要追到一手依据。原论文、规范、源码或最小实验用于解决具体疑点，不作为每篇必走的步骤。主线机制已经讲清、关键结论有依据、影响理解的疑点已解决或明确说明时，进入大纲或写作；不为凑来源数量、穷尽资料或展示研究深度继续扩张任务。

如果工作区有相关文档，先查看现有结构，只阅读与本篇有关的内容：

- 用户已指定分类时遵循。否则可建议归入已有分类或新增分类，说明理由，与用户讨论后确定；不得自行重组分类或移动旧文。
- 前置知识用具体概念描述。有对应文章时核实内容并链接；没有时直接说明预期读者了解哪些概念，继续本篇，不强制补写基础文章或编造链接。正文第一次用到已声明的前置概念时，用一两句话简短提醒与当前讲解有关的含义，再继续新内容，不展开成基础教程。
- 没有现成目录或文章索引也能写作，不要求先建立知识库系统。

大纲简洁呈现文章要解决的问题、必要基础、拟展开的章节、形成与演进的主线，以及有助于确认方向的例子或推导。归类建议可一并讨论。

**大纲按主题自然组织。** 问题、简单方案的不足、核心机制、实现与取舍是讲解关注点，无需一一对应章节。标题表达具体内容或疑问，不套固定的“背景—定义—原理—优缺点—总结”；不凑章节、不强求对称、不给每节机械加小结。质量检查留在内部，不要全部变成文章栏目。

## 确认后写作

默认采用问题驱动的叙述：从有意义的问题引出机制，帮助读者理解为什么这样设计。具体顺序与篇幅随主题调整。面向声明的读者基础，展开新增内容所需的关键论证，避免只罗列术语和优点。

- **自然的技术交流**：像理解较深的同事认真讲解，措辞自然、推理严谨。可适量使用“我们”，用连贯段落推进解释，避免套话、过度分点和机械问答；不刻意装口语，也不虚构个人经历。限定与辨析只在直接影响当前理解时出现，用具体解释承接上下文；不要把作者内部的准确性判断变成反复打断主线的旁白，也不要不断反驳尚未引出的假设性误解。
- **技术的发展脉络**：正文要讲清为何出现、出现前如何解决问题、原有方案的局限、新设计带来的变化，以及之后的关键演进和发展方向。围绕需求与设计的因果关系组织，与原理和取舍自然衔接；篇幅随主题调整，不强制设置固定历史栏目或堆砌年份、人物。区分已发生的演进、正在发展的方向与有依据的展望，展望说明所针对的问题，不把推测写成确定事实。
- **术语一致**：关键术语首次出现时给出常用中文名与英文名，必要时注明缩写；后文使用自然且一致的称呼，不反复标注全称。没有自然通行译名的词保留英文，不强行翻译。
- **原理与实现结合**：用伪代码优先表达核心步骤、输入输出与状态变化，并解释它们与原理的对应关系。注明重要简化假设，保留会影响理解的关键分支；语言语义、源码细节或真实运行验证确有需要时再用具体语言。
- **关键推导**：定义符号和假设，展开从前提到结论的关键步骤，常规计算适当省略。按主题使用数学，不要求每篇都有公式。
- **按需举例**：理论简单、文字已经能解释清楚时，不需要举例，也不要求每篇必有例子。确有帮助时，能自然贯穿就复用主例子，其他机制或边界情况可补充独立例子，不强行统一；需要时展示中间状态。类比要说明边界。
- **文字为主**：以连贯文字和伪代码解释，仅在难以清楚说明时配图；不设配图数量，不额外制作封面或装饰图。
- **深度与可读性**：讲清关键设计取舍与适用边界，用目录和自然章节组织长文。避免套话、重复总结和为了显得完整而扩展无关内容；不强制附加测验、FAQ 或固定结尾。

用户确认后，按大纲完成整篇并交付，不额外自动启动独立核验或评分。写作过程仍须以准确、有依据为要求，处理已发现的问题；一般措辞、例子和局部安排可在写作中改善，实质改变已确认主题范围或主线时先与用户对齐。

## 手动触发：核验与通读

仅在用户明确要求时运行，例如“检查这篇文章”或“对这篇文章做一次核验与通读”。读取当前文章及必要来源，检查事实、关键推导、伪代码逻辑、例子结果、术语、前置链接和全文连贯性，判断关键机制是否解释完整。核查范围以本篇主题与读者基础为准。

报告具体位置、问题、依据与修改建议，区分确定错误、表达缺口和仍无法核实的内容。无明显问题则如实说明已检查范围及限制，不虚构缺陷或给出未经证实的“完全正确”保证。不额外设置理解测试、自测题或数值评分。

检查本身不授权改稿。用户同时明确要求“检查并修正”时可以直接修正；否则等待用户给出修改建议或要求，再按相关内容范围执行。不要把尚未触发的核验标记为已完成。

## 交付

对于涉及真实实验的结论，保留实际环境与结果；伪代码不声称可直接运行，未执行的实验不声称已经验证。不要虚构引用、性能数据或用户经历。

文章保存为 `.md` 文件，文件名和位置遵循当前项目约定与已确认分类。没有现成约定时提出简洁的文件位置建议；未确定分类不妨碍研究和大纲准备。

**正文不加引用标记，参考资料统一列在文末。** 文末用资料标题和真实链接列出实际查阅并用于写作的材料。正文不插入引用编号、脚注或逐段来源链接；前置阅读与必要的学习导航链接仍可保留。保留对理解有意义的假设和限制说明。

将研究过程中关键结论与来源的对应关系及仍存疑之处简洁保存在单独的工作记录中，使用项目已有记录位置；若无约定，采用与文章可关联的研究记录文件名。仅在实际执行手动核验后追加相应结果。不要将检索流水账混入正文，不复制整篇外部材料。引用呈现仍须遵守运行环境中更高优先级的要求。

完成后给出文章链接和需要用户知道的具体限制，等待用户反馈。不自动发布，不因后续追问改动成稿，不宣称生成文章就代表用户已经掌握知识。
