# OSI 与 TCP/IP：网络分层如何让通信变得可理解

假设你已经能写一个客户端，把请求发给服务端，也知道 IP 地址和端口的大致用途。现在想再往下追问：程序交出去的字节，究竟怎样穿过网卡、交换机和路由器，最终变成另一个程序读到的数据？

这时，我们很容易遇到两张图：OSI 七层模型，以及 TCP/IP 四层或五层模型。把层名记下来并不难，真正让人困惑的是它们与实际通信的关系：为什么 IP 和 TCP 要分开？表示层、会话层在哪里？路由器为什么不需要像服务端一样把所有层都处理一遍？

本文从这些问题出发。读者只需了解客户端、服务端、IP 地址、端口和报文的基本含义，不必预先熟悉分层模型。我们会从早期网络面临的互联问题理解分层设计，再沿着一条具体路径看数据如何流动，最后看安全、规模与性能需求怎样推动协议继续演进。

## 一次通信，为什么需要这么多协议？

一个请求要成功，需要解决好几类性质不同的问题。

服务端首先要知道收到的数据是什么意思：这是查询订单，还是提交文件？字段用什么格式表示，一条请求到哪里结束？这需要通信双方约定消息的语义与表示方式。

但是，即使双方认识同一种消息，数据也未必能按预期到达。网络可能丢包、乱序或者重复传输。如果应用需要连续、有序的数据，就得有人识别缺失、安排重传，并控制发送速度。

再往下看，客户端和服务端可能处在两个不同的网络。数据不能只在当前局域网里传递，还需要经过中间设备，逐步走到目标网络。

而每一段路径本身又有具体的传输条件：通过哪块网卡、采用什么帧格式、如何把比特变成介质上的信号。这些条件可能随着路径变化。

假如把所有职责塞进一个协议，每个应用都要同时考虑业务格式、丢包恢复、路径选择和网卡差异。更换一种接入技术，可能迫使上层重新适配；修改一种消息格式，也可能牵动底层通信。系统越大，变化之间的耦合就越难控制。

**分层的作用，是为一部分变化建立边界。** 某一层通过相对稳定的服务向上暴露能力，上层依据这些能力工作，而不必掌握下层的全部实现。只要边界上的行为保持兼容，下层就有机会独立调整。

这些层仍然相互依赖：底层丢包会影响传输性能，传输速度会影响应用响应。划清职责之后，我们就能沿着依赖关系分析这些影响。

分层也有代价。各层可能引入自己的控制信息和状态，处理数据时需要解析、转换或协调；一个过于封闭的接口，还可能让上层拿不到优化决策所需的信息。因此，评价分层设计时，需要同时看它隔离了哪些变化，又增加了哪些开销和限制。

## 从一张网络，到把不同网络连起来

TCP/IP 的职责边界是在解决互联问题的过程中逐渐形成的。

早期 ARPANET 的主机通过网络控制协议（Network Control Protocol，NCP）通信，远程登录、文件传输等应用建立在这套通信能力之上。NCP 面向 ARPANET 的环境，依赖该网络提供可靠传递，对其他独立网络中的目标也缺少相应的寻址能力。

当分组无线网络、分组卫星网络也要参与通信时，问题变了：一个网络里的主机，需要访问另一个网络中的计算机，而各网络有各自的传输条件与内部设计。如果要求它们全部改造成同一种网络，互联就会被每个网络的改造进度限制。新的方案需要让网络保留内部实现，通过中间的网关交换数据，并在端点处理跨越整条路径的通信问题。

1974 年的 RFC 675 描述了早期的传输控制程序（Transmission Control Program，TCP）。这时的 TCP 方案同时涉及端到端传输与跨网络传递，还没有形成今天 TCP 和 IP 各自负责一部分工作的组合。

把这两种工作放在一起，会让转发机制与端点的传输控制相互牵连。1977 年，Jon Postel 在 IEN 2 中提出把它们分开：一个协议负责跨网络包装与传递，另一个协议负责主机之间的端到端通信。后来形成的互联网协议（Internet Protocol，IP）提供数据报的寻址与传递，TCP 则在其上处理可靠传输等工作。

这种拆分也给不同应用留下了选择。传文件时，少一段内容都可能使结果不可用，需要可靠交付；实时语音却可能更在意及时播放，等丢失的数据重传回来时，它的播放时机已经过去。把跨网络传递单独抽出来，应用就能根据需要选用 TCP，或者使用用户数据报协议（User Datagram Protocol，UDP）并自行安排所需的传输处理。

协议设计完成之后，还要让已有系统迁移。1981 年的 RFC 801 制定了从 NCP 转向 TCP/IP 的计划，包括主机实现新协议、迁移应用，以及通过中继服务帮助过渡。ARPANET 在 1983 年 1 月 1 日切换到 TCP/IP。这个过程同时涉及底层通信能力和依赖它的应用，协议栈要成为共同基础，需要实现与部署一起配合。

现在就能更具体地理解分层的价值：网络可以保留不同的内部技术，端点通过共同的跨网络服务通信；传输方式也可以按应用需求选择。接下来，我们用协议、服务与接口把这些边界说清楚。

## 理解分层，先分清协议、服务与接口

在一张协议栈图中，上下方向和左右方向表达的是两种不同关系。

**服务（Service）**描述一层向上提供什么能力。以传输控制协议（Transmission Control Protocol，TCP）为例，应用可以在连接上发送和接收有序的字节流，不需要自己为每个丢失的数据段安排重传。这是应用观察到的传输服务。

**协议（Protocol）**描述通信对等方需要遵守的规则。两端 TCP 如何使用序号、确认信息和控制标志来维护连接，属于 TCP 协议。协议既包含报文格式，也包含收到报文、计时器到期等事件发生时的行为；双方仅仅知道如何解析字段，还不足以正确协作。

**接口（Interface）**则是本机使用服务的具体方式。应用可能通过套接字（Socket）接口访问 TCP，例如建立连接、提交数据和读取数据。

应用通过接口提交字节之后，本机 TCP 按协议组织发送；远端 TCP 根据报文与连接状态处理数据，再让远端应用通过自己的接口读取。

我们可以把两个方向写成：

```text
本机：应用 ──使用服务的接口──> TCP 实现 ──使用下层服务──> IP 实现

两端：本机 TCP 实现 <──遵循 TCP 协议的逻辑通信──> 对端 TCP 实现
```

第二行中的“逻辑通信”，指的是两端 TCP 按同一套规则解释报文并维护连接状态。它们交换的报文由 IP 和链路承载，穿过实际网络。

这也解释了为什么更换操作系统后，套接字接口的细节可以不同，网络通信仍然成立：**双方必须兼容的是线上协议行为，本地接口与内部代码组织可以不同。**

接收端 TCP 按序交付字节之后，应用还需要解析请求、执行操作并返回结果。传输与业务处理分别完成各自的工作。

## OSI 七层分别划出了什么边界？

开放系统互连（Open Systems Interconnection，OSI）参考模型将通信职责划分为七层，为不同系统之间的互通与标准协调提供共同框架。

不同系统要实现互通，需要协调的不只是数据如何穿过网络，还包括传输控制、对话组织、数据表示与应用交互。如果各项标准对职责的划分不同，就很难判断哪些规范应该配合、哪里仍缺少共同约定。OSI 通过统一的层次与术语，为这些标准提供组织框架。ISO 在 1984 年发布了 ISO 7498 的第一版，后来更新为 ISO/IEC 7498-1。

下面按从下到上的顺序，概括每层关注的问题。

| 层 | 名称 | 主要关注的问题 |
|---|---|---|
| 1 | 物理层（Physical Layer） | 如何通过传输介质发送和接收比特 |
| 2 | 数据链路层（Data Link Layer） | 如何组织链路上的数据帧与传输过程 |
| 3 | 网络层（Network Layer） | 如何通过一个或多个网络实现寻址与传递 |
| 4 | 传输层（Transport Layer） | 如何为通信端点提供所需的端到端传输服务 |
| 5 | 会话层（Session Layer） | 如何组织、协调与同步通信双方的对话 |
| 6 | 表示层（Presentation Layer） | 如何使双方对交换数据的表示达成一致 |
| 7 | 应用层（Application Layer） | 如何支持应用所需的通信语义与交互 |

七层划分考虑了职责差异、抽象层次与标准协调的需要。层太少，会把性质不同的问题挤在一起；层太多，又会增加难以解释和协调的边界。OSI 在这些取舍之间选择了上面的七层结构。

### 网络层与传输层：到达目标，和提供所需的传输服务

在 Internet 中，IP 处理地址与数据报的跨网络传递。IP 地址用来标识接口等网络通信对象，帮助设备决定数据应当往哪里走。

然而，“向目标传递数据报”和“让应用获得完整、有序的内容”是两个问题。一次 IP 转发成功，只说明这一跳完成了相关处理，不能推导出后面的路径没有丢失。

TCP 在 IP 提供的数据报服务之上，为应用提供有序字节流。UDP 则提供另一种传输方式，不为应用补上 TCP 那样的重传与按序交付。两者都属于 Internet 的传输层，却提供不同的服务。

端口帮助传输实现区分应用服务和数据流。同一个服务端端口可以服务很多连接；识别一条 TCP 连接，还要结合两端的地址与端口。

### 会话层与表示层：管理对话，和理解表示

这两层常让人困惑，因为我们很少在日常开发中看到两个明确命名的独立模块。

表示层关心的是：双方如何用共同认可的表示交换信息？即使比特完整到达，双方对字段编码的理解不同，也无法正确交流。因此需要约定传输表示，必要时进行转换。序列化就涉及这类工作：把内存中的数据组织成约定格式，使接收方能够按同一规则还原。

会话层关注对话的组织和同步，例如协调双方的交互过程，设置同步点，以及在需要时从约定的同步点恢复对话。

在实际系统中，这些工作通常由具体协议或公共库承担。数据经过序列化，再按协议约定进行交互；从代码中看到的可能是若干函数或组件。

### 应用层：约定应用之间如何交互

应用层约定应用之间的通信方式：一端可以请求哪些操作、请求包含哪些信息、另一端如何响应。服务端收到请求后，按这些约定理解操作及其参数，处理完成后再组织响应。这样，两端应用才能通过消息协作。

## TCP/IP 为什么采用另一种划分？

TCP/IP 通常也指 Internet 协议族（Internet Protocol Suite），范围远大于 TCP 和 IP 两个协议。我们所说的 TCP/IP 模型，是对这套网络体系职责的分层描述。

回看两者的形成过程，OSI 提供了组织互通标准的七层参考框架；TCP/IP 则在互联方案、协议实现与网络部署中逐步发展，形成了具体的协议族。今天我们用 OSI 梳理通信职责，用 TCP/IP 解释 Internet 的实际协议组合。理解这两种用途，也就能理解为什么它们的层次划分不完全相同。

RFC 1122 将其分为应用层、传输层、互联网层和链路层。为了单独讲解信号传输与帧处理，一些教材又把底部展开成物理层和数据链路层，得到五层教学模型。

| TCP/IP 四层描述 | 常见五层教学画法 | 与 OSI 对照时的观察方式 |
|---|---|---|
| 应用层 | 应用层 | 观察应用通信，以及上部的数据表示、对话组织等职责 |
| 传输层 | 传输层 | 观察端到端传输服务 |
| 互联网层 | 网络层 | 观察 IP 寻址与跨网络传递 |
| 链路层 | 数据链路层、物理层 | 分别观察链路传输与比特传输 |

OSI 对上部通信职责作了较细的划分；TCP/IP 的应用层内部则可以包含负责数据表示、交互组织等工作的协议与组件。表中按职责作了大致对应，方便我们把两种分层方式联系起来。

对 Internet 分层更有解释力的问题是：**不同的应用与不同的网络，如何通过共同的 IP 服务衔接？**

下层的链路技术可以不同，上层的应用和传输需求也可以不同。只要各段网络能够承载 IP 数据报，端点就可以在其上组合所需协议。应用不需要知道每一段链路采用的具体帧格式，沿途网络也不需要为每一种业务分别设计转发方式。

这种边界降低了协作所需的共同约定，但也留下了需要上层处理的问题：IP 不承诺端到端可靠交付，应用也不能把网络视为永远正常的通道。TCP/IP 的分层价值，正是在这些能力与限制的组合中体现出来的。

## 跟着一份数据经过客户端、路由器和服务端

为了看清不同层的作用，我们使用一条刻意简化的路径：两个以太网子网，由一台路由器连接。客户端已经知道服务端的 IP 地址，并已建立 TCP 连接，接下来发送一个 HTTP/1.1 请求。

超文本传输协议（Hypertext Transfer Protocol，HTTP）在这里负责请求与响应的格式和含义。暂时使用明文 HTTP，安全传输放到下一节讨论。

```text
客户端 C                 路由器 R                  服务端 S
10.0.1.10/24 ─── 10.0.1.1/24 | 10.0.2.1/24 ─── 10.0.2.20/24
   端口 50000                                      端口 8080
```

`/24` 表示地址的前 24 位作为这里的子网前缀，所以客户端与服务端属于不同子网。路由器的两个接口分别连接这两个子网。我们假设路由配置正确，链路正常，报文足够小而不需要 IP 分片，也没有地址转换、隧道或代理。

### 客户端：同一份数据，在不同层有不同身份

应用先按 HTTP/1.1 的规则组织请求，再通过套接字提交字节。这时，应用关心的是“我要请求哪个资源”；TCP 关心的则是“这些字节属于哪条连接，在字节流中处于什么位置”。

TCP 可以根据发送状态与可用报文大小，把字节流的一部分放入一个 TCP 段（Segment）。该段带有源端口、目的端口、序号等 TCP 信息。随后，IP 用一个数据报（Datagram）承载它，并加上源地址、目的地址及其他 IP 信息。

对客户端来说，服务端不在本地子网，需要经网关转发。因此，它选择路由器的左侧接口作为下一跳，也就是先接收并继续转发这份数据的邻接节点。

在以太网上，这个 IP 包需要放入一个数据帧（Frame）。客户端使用自己的媒体访问控制地址（Media Access Control Address，MAC 地址）作为源 MAC，以路由器左侧接口的 MAC 作为目的 MAC。MAC 地址帮助这一段以太网完成帧的交付。

如果还不知道下一跳的 MAC，IPv4 以太网环境通常通过地址解析协议（Address Resolution Protocol，ARP）获取对应关系。完成解析后，客户端就能填写帧的目的 MAC。这里假设该映射已经可用。

选取一个携带请求字节的 TCP 段，其封装关系可以示意为：

```text
以太网首部 | IPv4 首部 | TCP 首部 | 请求字节的一部分 | 以太网帧校验序列
```

**封装（Encapsulation）**让一层把上层交来的数据作为载荷，并加入完成自身职责所需的信息。TCP 序号帮助接收端处理字节顺序，IP 地址支持路径上的转发，目的 MAC 支持这一段链路上的交付。它们解决的问题不同，因此需要同时存在。

在 OSI 的通用术语中，一层交给下层传送的数据可以称为服务数据单元（Service Data Unit，SDU）；由某层协议组织、供该层对等实体理解的单位称为协议数据单元（Protocol Data Unit，PDU）。例如 TCP 段是 TCP 的 PDU，同时又成为 IP 承载的上层数据。

一个 HTTP 请求可能跨多个 TCP 段，一个 TCP 段也可能携带连续字节流中来自不同应用写入的数据。TCP 不保留应用调用的消息边界，所以图中写的是“请求字节的一部分”。

### 路由器：拆掉当前链路封装，再决定下一跳

帧到达路由器后，链路接收处理取出其中的 IP 包。路由器检查 IP 信息，发现目的地址 `10.0.2.20` 不是自己的地址，于是进入转发处理。

这里需要区分两个事实：**这一帧交给了路由器，但其中的 IP 包最终交给服务端。** 链路上的接收方和端到端通信的接收方可以不同。

路由器根据目的 IP 查找路由。在这个例子中，目标位于右侧接口直连的子网，所以输出接口是右侧接口，下一跳就是服务端。转发时还要处理 IPv4 的生存时间（Time to Live，TTL）：每经过路由转发，它的值都会减少，耗尽时包会被丢弃，从而避免包持续在网络中循环。

路由器将 TTL 减少，再更新 IPv4 首部校验和，最后把包放入适合右侧链路的新帧。假设客户端发出时 TTL 为 64，那么经过这一次正常转发后为 63。

| 信息 | 客户端到路由器 | 路由器到服务端 |
|---|---|---|
| 源 MAC | 客户端接口的 MAC | 路由器右侧接口的 MAC |
| 目的 MAC | 路由器左侧接口的 MAC | 服务端接口的 MAC |
| 源 IPv4 地址 | `10.0.1.10` | `10.0.1.10` |
| 目的 IPv4 地址 | `10.0.2.20` | `10.0.2.20` |
| TCP 源端口 / 目的端口 | `50000 / 8080` | `50000 / 8080` |
| IPv4 TTL | `64` | `63` |

用伪代码表达本例中路由器的核心职责，可以写成：

```text
function handle_ipv4(packet):
    if not valid_ipv4_header(packet):
        discard(packet)
        return

    if destination_is_local(packet.destination):
        deliver_to_local_ip_stack(packet)
        return

    route = lookup_route(packet.destination)
    if route is missing:
        handle_no_route(packet)
        return

    if packet.ttl <= 1:
        handle_ttl_expired(packet)
        return

    packet.ttl = packet.ttl - 1
    update_ipv4_header_checksum(packet)

    # 下一跳邻居信息在本例中已经可用
    next_mac = cached_mac(route.interface, route.next_hop)
    frame = ethernet_encapsulate(
        source_mac = route.interface.mac,
        destination_mac = next_mac,
        payload = packet
    )
    enqueue_for_transmission(route.interface, frame)
```

这段伪代码承接链路接收处理，展示本例中的 IPv4 转发步骤；为突出主线，省略了安全策略、IP 选项、分片、邻居解析失败和发送队列异常等处理。

值得观察的是：这里没有读取 HTTP 路径，也没有维护客户端与服务端之间的 TCP 字节流。完成普通 IP 转发所需的信息已经在相关层提供，不必把载荷中的每一种协议都解释一遍。

### 服务端：知道该交给谁，比单纯去掉首部更重要

新帧到达服务端后，链路处理取出 IPv4 包。IP 发现目标是本机，然后依据包内标识上层协议的信息，把载荷交给 TCP 处理。

TCP 再用两端地址与端口定位连接，依据连接状态检查报文，并处理字节排序、重复数据和确认等事项。可交付的字节进入接收缓冲区，应用通过套接字读取它们，再按 HTTP 的规则识别完整请求。

这个过程中，**解封装（Decapsulation）**负责验证和解释当前层的信息，**分用（Demultiplexing）**负责将数据交给对应的协议或通信对象。服务端正是通过这些步骤，把网卡收到的帧逐步交付给正确的连接与应用。

TCP 向应用提供字节流，这一点可以在一个极小的例子中看清。假设应用依次提交两段字节：

```text
write("AB")
write("CD")
```

接收端可能一次读到 `"ABCD"`，也可能分成 `"A"` 与 `"BCD"`。这两种情况都可能符合 TCP 的服务约定。TCP 保持的是流中的字节顺序，不是两次 `write` 的边界。应用如果需要识别消息，就要通过协议约定长度、分隔符或其他结构。

因此，HTTP 解析器通常需要累积字节，再判断请求是否完整，而不能把“一次读取结束”当作“一条请求结束”。这是从传输服务边界直接推导出的应用设计要求。

现在再看整条路径：链路帧在经过路由器时被替换，IP 包按目标地址逐跳转发，TCP 的连接状态由两端维护，HTTP 请求则由应用端点解释。这些职责一起完成了从客户端到服务端的通信。

## 真实协议为什么不总能整齐地放进格子？

前面的例子中，HTTP、TCP、IP 与以太网形成了清晰的承载关系。加入 TLS 和 QUIC 后，协议之间会出现更多组合，也更能看出实际网络如何安排各项职责。

### TLS：给字节流增加安全性质

当网络承载账号、交易与私人通信时，仅仅让字节完整到达还不够。TCP 的可靠交付不会自动隐藏内容，也不能证明对端就是预期的服务；通信还需要抵御窃听、篡改和冒充。这些需求推动了安全协议的发展。

传输层安全协议（Transport Layer Security，TLS）在常见的基于 TCP 的 HTTPS 连接中，位于 HTTP 与 TCP 之间。以 HTTP/1.1 为例，承载关系可以写成：

```text
HTTP/1.1 → TLS → TCP → IP → 链路
```

TLS 使用底层可靠、有序的数据流，向上提供具有认证、机密性和完整性保护的安全通道。常见 HTTPS 使用证书认证服务器；客户端是否通过 TLS 认证，则取决于具体配置和协议使用方式。

因此，TCP 连接可以成功建立并传递握手字节，TLS 握手却因为认证等问题失败。反过来，TLS 也需要底层传输持续工作，无法靠加密让一条已经断开的网络路径继续传递数据。

从分层关系看，TLS 在 TCP 的字节流服务上增加了安全保护，HTTP 使用这条安全通道交换请求与响应。

### QUIC：在 UDP 之上，也可以提供传输服务

传输性能也会推动职责重新组合。HTTP/2 已经能把多个逻辑流放在同一条 TCP 连接上，但 TCP 向上交付的是一条有序字节流。如果前面的一段字节丢失，后续字节就要等待缺口补齐，即使其中包含另一个逻辑流的数据。这种队头阻塞（Head-of-Line Blocking）使一次丢包可能延迟多个请求的处理。

QUIC 将可靠、有序交付组织到各个流内部。某个流缺少数据时，其他流中已经完整收到的数据仍有机会继续交付；各流同时共享连接的拥塞控制。它还把安全与传输握手结合起来，减少建立安全连接时需要分开进行的交互。

QUIC 的报文由 UDP 数据报承载，但 QUIC 本身向应用提供传输能力，包括可靠的流、多路复用、流量控制与拥塞控制，并集成 TLS 握手。HTTP/3 使用 QUIC 承载 HTTP 通信，其关系可以概括为：

```text
HTTP/3 → QUIC → UDP → IP → 链路
          └─ 集成 TLS 握手与相关安全机制
```

QUIC 使用自己的报文保护机制，并通过集成的 TLS 握手建立相关密钥。UDP 为它承载数据报，QUIC 则在这些数据报之上管理可靠的流和安全通信，HTTP/3 直接使用这些能力。

因此，网络中的传输能力可以通过多种协议组合来实现。理解 QUIC 的作用，需要沿着这条承载关系，看到每个协议向上提供了什么能力。

### 判断设备职责，要看它对这段通信做了什么

前面的路由器只做普通 IP 转发，所以没有终止两端 TCP 连接。但一台同时执行网络地址转换（Network Address Translation，NAT）的设备，可能修改地址，端口转换还会涉及传输层字段；代理则可能成为客户端连接的对端，再建立另一段上游连接。

这些功能会改变设备参与通信的方式。普通转发根据目标地址继续传递包，地址转换修改相关字段，代理则参与两段连接的数据交换。分析具体网络时，需要沿着实际路径识别设备承担的功能。

### 用分层缩小问题范围，而不是凭层号直接下结论

假设一次 HTTPS 访问失败，可以依次检查几个不同的事实：有没有获得目标地址、是否存在可用路径、传输连接是否建立、安全握手是否完成、应用是否返回了有效响应。这些事实对应不同职责，也提供不同强度的证据。

域名系统（Domain Name System，DNS）负责域名解析，属于应用层协议。用域名访问服务时，客户端通常先获得目标地址，再向该地址建立连接。因此，可以先确认解析结果，再继续观察连接过程。

如果已经收到了目标服务的 HTTP 响应，就可以继续根据响应内容判断问题。例如权限不足或服务处理失败，通常需要进一步查看认证信息或服务端日志。

如果只知道 TCP 建连超时，定位就远没有那么明确。路径不可达、过滤策略、对端不可用等都可能导致相似现象，需要更多观察来区分。**症状出现在哪个接口，不足以证明根因只在对应层。**

## 网络继续演进时，哪些问题还在变化？

从早期互联到 TLS 与 QUIC，可以看到分层体系内部持续发生的变化。沿着这些已经出现的设计，后续演进仍有几个具体问题需要解决。

首先是规模。IPv4 使用 32 位地址；IPv6 将地址扩展到 128 位，为更大的网络规模提供地址空间，并调整首部组织方式。它继续提供跨网络的数据报服务，上层仍然可以使用 TCP、UDP 等协议。扩大地址空间之后，实际通信还依赖端点实现、网络支持与部署配合，迁移本身也是工程问题。

其次是移动环境中的连接连续性。普通 TCP 连接用两端的地址与端口识别，设备切换网络、地址改变时，原连接通常难以直接沿用。QUIC 使用连接标识符（Connection ID），并配合路径验证等机制，支持客户端将连接迁移到新的网络路径。这里改变的是传输连接与路径之间的关系，IP 仍负责在当前路径上传递数据报。

还有一个问题是，新传输机制怎样穿过已有网络并进入应用。QUIC 采用 UDP 承载，目的之一就是利用已经存在的 UDP 支持来降低部署门槛。协议能否演进，既取决于设计提供了什么能力，也取决于端点和沿途设备能否支持它。缩短连接建立过程、改善多流传输、适应路径变化，都要与这个部署条件一起考虑。

这些方向分别落在地址体系、传输服务与协议部署上。OSI 的职责划分仍能帮助我们辨认问题，TCP/IP 的具体协议则继续调整承担这些职责的方式。学习新协议时，可以沿用同一条思路：先看旧方案遇到了什么限制，再看新协议提供的服务、依赖的下层能力，以及它把哪些状态放在了哪些端点。
